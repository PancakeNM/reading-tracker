# Feature Specification: Доменное ядро учёта чтения (Reading)

**Feature Branch**: `001-reading-domain-core`
**Created**: 2026-10-11
**Status**: Draft
**Input**: User description: "Написать чистое ядро (Domain Layer) на Go и покрыть его тестами. Описать структуры из дизайн-документа в коде. Реализовать бизнес-методы `func (r *Reading) UpdateProgress(page int) error` и `func (r *Reading) Complete(rating int, finishDate time.Time) error` со всеми проверками. Покрыть оба метода табличными unit-тестами: happy path и все негативные сценарии (страница < 0, страница > максимума, оценка = 0, оценка = 6, дата из 2030 года)."

## Clarifications

### Session 2026-10-11

- Q: Что делать при обновлении прогресса, если статус «хочу прочитать» (чтение ещё не начато)? → A: Автоматически перевести в «читаю» и зафиксировать дату старта = текущий момент.
- Q: Что делать при завершении чтения, если статус уже «прочитано» или «брошено»? → A: Отказать в обоих случаях (так же, как при обновлении прогресса).
- Q: Что делать при завершении чтения, если дата старта не задана? → A: Отказать: без даты старта завершить чтение нельзя.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Обновление прогресса чтения (Priority: P1)

Пользователь читает текстовую книгу и отмечает, на какой странице он сейчас. Система принимает только осмысленный прогресс: страница не может быть отрицательной и не может превышать число страниц издания. Нельзя менять прогресс по уже прочитанной или брошенной книге. Когда пользователь отмечает последнюю страницу, книга автоматически считается прочитанной, и дата окончания фиксируется.

**Why this priority**: отметка прогресса — самое частое действие сервиса. Без него статус «читаю» не имеет смысла, а остальные сценарии (завершение, оценка) опираются на корректный прогресс.

**Independent Test**: создать чтение в статусе «читаю» с известным числом страниц, передать разные значения страницы и проверить результат (принято или отклонено), а также итоговые прогресс, статус и даты.

**Acceptance Scenarios**:

1. **Given** чтение в статусе «читаю», всего 300 страниц, прогресс 10, **When** пользователь отмечает страницу 150, **Then** операция успешна, прогресс = 150, статус остаётся «читаю», дата окончания не задана.
2. **Given** чтение в статусе «читаю», всего 300 страниц, **When** пользователь отмечает страницу 0, **Then** операция успешна, прогресс = 0.
3. **Given** чтение в статусе «читаю», всего 300 страниц, **When** пользователь отмечает страницу 300, **Then** операция успешна, прогресс = 300, статус «прочитано», дата окончания = текущий момент.
4. **Given** чтение в статусе «хочу прочитать», дата старта не задана, **When** пользователь отмечает страницу 20, **Then** операция успешна, прогресс = 20, статус «читаю», дата старта = текущий момент.
5. **Given** чтение в статусе «читаю», прогресс 120, **When** пользователь отмечает страницу 80, **Then** операция успешна, прогресс = 80 (откат допустим).
6. **Given** чтение в статусе «читаю», **When** пользователь отмечает страницу −1, **Then** операция отклонена с ошибкой «отрицательная страница», состояние чтения не изменилось.
7. **Given** чтение в статусе «читаю», всего 300 страниц, **When** пользователь отмечает страницу 301, **Then** операция отклонена с ошибкой «страница больше числа страниц издания», состояние чтения не изменилось.
8. **Given** чтение в статусе «прочитано», **When** пользователь отмечает любую страницу, **Then** операция отклонена с ошибкой «чтение уже завершено», состояние не изменилось.
9. **Given** чтение в статусе «брошено», **When** пользователь отмечает любую страницу, **Then** операция отклонена с ошибкой «чтение уже завершено», состояние не изменилось.

### User Story 2 - Завершение чтения с оценкой (Priority: P1)

Пользователь дочитал книгу и явно отмечает её прочитанной: ставит оценку от 1 до 5 и указывает дату окончания. Дата окончания не может быть в будущем и не может быть раньше даты старта. После завершения прогресс автоматически становится равным числу страниц издания.

**Why this priority**: завершение с оценкой — второй ключевой бизнес-метод из задачи. Он фиксирует итог чтения и оценку и защищает инвариант «оценка только 1–5».

**Independent Test**: создать чтение в статусе «читаю» с известной датой старта, вызвать завершение с разными оценками и датами и проверить результат, статус, оценку, дату окончания и прогресс.

**Acceptance Scenarios**:

1. **Given** чтение в статусе «читаю», всего 300 страниц, прогресс 120, дата старта 2026-09-01, **When** пользователь завершает с оценкой 4 и датой окончания 2026-10-05, **Then** операция успешна, статус «прочитано», оценка = 4, дата окончания = 2026-10-05, прогресс = 300.
2. **Given** то же чтение, **When** пользователь завершает с оценкой 1, а затем (на отдельной копии) с оценкой 5, **Then** обе операции успешны (границы диапазона допустимы).
3. **Given** то же чтение, **When** пользователь завершает с датой окончания, равной дате старта, **Then** операция успешна.
4. **Given** то же чтение, **When** пользователь завершает с оценкой 0, **Then** операция отклонена с ошибкой `ErrInvalidRating`, состояние не изменилось.
5. **Given** то же чтение, **When** пользователь завершает с оценкой 6, **Then** операция отклонена с ошибкой `ErrInvalidRating`, состояние не изменилось.
6. **Given** то же чтение, текущий момент — октябрь 2026, **When** пользователь завершает с датой окончания в 2030 году, **Then** операция отклонена с ошибкой «дата окончания в будущем», состояние не изменилось.
7. **Given** то же чтение с датой старта 2026-09-01, **When** пользователь завершает с датой окончания 2026-08-31, **Then** операция отклонена с ошибкой «дата окончания раньше даты старта», состояние не изменилось.
8. **Given** чтение без даты старта, **When** пользователь завершает с корректной оценкой и датой, **Then** операция отклонена с ошибкой «дата старта не задана», состояние не изменилось.
9. **Given** чтение в статусе «прочитано» или «брошено», **When** пользователь завершает с корректной оценкой и датой, **Then** операция отклонена с ошибкой «чтение уже завершено», состояние не изменилось.

### User Story 3 - Модель предметной области из дизайн-документа (Priority: P2)

Разработчик сервиса получает в ядре описания всех сущностей из `DESIGN.md` (раздел 4) и новой сущности «Чтение». На них опираются следующие слои: хранилище, HTTP API.

**Why this priority**: сущности нужны как фундамент, но сами по себе бизнес-ценности не дают. Поведение в этой фиче есть только у «Чтения».

**Independent Test**: проверить, что для каждой сущности из `DESIGN.md` §4 в ядре есть соответствующее описание с теми же полями, той же обязательностью полей и тем же смыслом, и что ядро собирается без внешних зависимостей.

**Acceptance Scenarios**:

1. **Given** список сущностей `DESIGN.md` §4 (User, Book, TextBook, AudioBook, Author, BookAuthor, Series, ReadingStatus, ShelfItem, ReadingLog, Review, AcquisitionType, Currency, BookOwnership), **When** ревьюер сверяет его с ядром, **Then** каждая сущность представлена, а поля и их обязательность (nullable, отмеченные `*`) совпадают.
2. **Given** доменное ядро, **When** его собирают и тестируют на машине без сети, базы данных и внешних сервисов, **Then** сборка и все тесты проходят.

---

### Edge Cases

- Страница ровно 0 допустима. Страница ровно равна числу страниц издания допустима и автоматически завершает чтение.
- Отметка последней страницы из статуса «хочу прочитать» одной операцией выставляет дату старта и дату окончания (обе равны текущему моменту), а статус становится «прочитано».
- Автозавершение через последнюю страницу не выставляет оценку: она остаётся пустой.
- Если дата старта уже была задана, при переходе «хочу прочитать» → «читаю» она не перезаписывается.
- Дата окончания, равная текущему моменту, не считается «в будущем».
- Даты сравниваются как моменты времени, а не как календарные дни. Окончание в тот же день, но раньше по времени, чем старт, отклоняется.
- Если нарушено сразу несколько правил, возвращается одна ошибка по фиксированному порядку проверок (см. FR-012), чтобы поведение было предсказуемым и тестируемым.
- Любая отклонённая операция не меняет ни одно поле чтения (атомарность).
- Тест «дата из 2030 года» не должен зависеть от реальных системных часов: он обязан проходить и после 2030 года.

## Requirements *(mandatory)*

### Functional Requirements

**Модель**

- **FR-001**: Ядро MUST содержать описания всех сущностей из `DESIGN.md` §4 с теми же полями, той же обязательностью полей и теми же связями.
- **FR-002**: Ядро MUST содержать сущность «Чтение» (Reading) с полями: статус, текущий прогресс (страница), число страниц издания (TotalPages), дата старта (может отсутствовать), дата окончания (может отсутствовать), оценка (может отсутствовать).
- **FR-003**: Статус чтения MUST принимать одно из четырёх значений: «хочу прочитать», «читаю», «прочитано» (Completed), «брошено» (Dropped). Статусы «прочитано» и «брошено» считаются завершающими.
- **FR-004**: Доменное ядро MUST NOT зависеть от хранилища, сети, HTTP и внешних сервисов.

**Обновление прогресса (UpdateProgress)**

- **FR-005**: Система MUST отклонять обновление прогресса, если статус чтения завершающий («прочитано» или «брошено»). Ошибка: «чтение уже завершено».
- **FR-006**: Система MUST отклонять страницу меньше 0. Ошибка: «отрицательная страница».
- **FR-007**: Система MUST отклонять страницу больше TotalPages. Ошибка: «страница больше числа страниц издания».
- **FR-008**: При корректной странице система MUST установить прогресс равным переданной странице. Уменьшение прогресса допустимо.
- **FR-009**: Если статус был «хочу прочитать», система MUST перевести его в «читаю» и, если дата старта не задана, установить её равной текущему моменту.
- **FR-010**: Если переданная страница равна TotalPages, система MUST перевести статус в «прочитано» и установить дату окончания равной текущему моменту. Оценка при этом не меняется.

**Завершение чтения (Complete)**

- **FR-011**: При успешном завершении система MUST установить статус «прочитано», оценку равной переданной, дату окончания равной переданной и прогресс равным TotalPages.
- **FR-012**: Проверки завершения MUST выполняться в таком порядке. При первом нарушении возвращается соответствующая ошибка:
  1. статус завершающий («прочитано» или «брошено») → «чтение уже завершено»;
  2. оценка вне диапазона 1–5 включительно → `ErrInvalidRating`;
  3. дата старта не задана → «дата старта не задана»;
  4. дата окончания позже текущего момента → «дата окончания в будущем»;
  5. дата окончания раньше даты старта → «дата окончания раньше даты старта».
- **FR-013**: Проверки обновления прогресса MUST выполняться в таком порядке: статус (FR-005), затем нижняя граница страницы (FR-006), затем верхняя граница (FR-007).

**Общие правила**

- **FR-014**: Любая отклонённая операция MUST оставлять все поля чтения без изменений.
- **FR-015**: Каждая причина отказа MUST быть отдельной именованной ошибкой, которую вызывающий код может однозначно распознать. Ошибка неверной оценки MUST называться `ErrInvalidRating`.
- **FR-016**: «Текущий момент» MUST быть подменяемым в тестах, чтобы проверки «в будущем» и автоматические даты были детерминированными.

**Тестирование и процесс (по конституции проекта)**

- **FR-017**: Каждый из двух методов MUST быть покрыт табличными тестами: каждая строка таблицы — отдельный именованный подтест. Таблица включает happy path и все негативные сценарии: страница < 0, страница > TotalPages, оценка = 0, оценка = 6, дата окончания в 2030 году. Также покрыты завершающие статусы, дата раньше старта и отсутствие даты старта.
- **FR-018**: Тесты MUST располагаться в отдельных тестовых файлах, не смешиваясь с кодом реализации.
- **FR-019**: Для каждого метода история версий MUST содержать коммит с падающими тестами (`test: add failing tests for Reading.<Метод>`) раньше коммита реализации (`feat: implement Reading.<Метод> logic`). Схлопывать или переставлять эти коммиты запрещено.

### Key Entities *(include if feature involves data)*

- **Reading (Чтение)**: одно чтение пользователем конкретного текстового издания. Атрибуты: статус, текущая страница, число страниц издания, дата старта, дата окончания, оценка 1–5. Инварианты: 0 ≤ текущая страница ≤ число страниц; если статус «прочитано» и дата окончания задана, то она не раньше даты старта; оценка, если задана, — от 1 до 5. Новая сущность, в `DESIGN.md` её нет; введена по указанию пользователя, которое по конституции важнее `DESIGN.md`.
- **Статус чтения**: «хочу прочитать», «читаю», «прочитано», «брошено». Расширяет стартовый набор `ReadingStatus` из `DESIGN.md` §4.8 значением «брошено».
- **Сущности `DESIGN.md` §4** (User, Book, TextBook, AudioBook, Author, BookAuthor, Series, ReadingStatus, ShelfItem, ReadingLog, Review, AcquisitionType, Currency, BookOwnership): только данные, без бизнес-поведения в рамках этой фичи.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% функциональных требований FR-005 – FR-015 подтверждены хотя бы одним автоматическим сценарием. Все пять обязательных негативных сценариев из задачи (страница −1, страница TotalPages+1, оценка 0, оценка 6, дата в 2030 году) присутствуют.
- **SC-002**: В 100% негативных сценариев состояние чтения после отказа полностью (по всем полям) совпадает с исходным.
- **SC-003**: Набор тестов детерминирован: 100 повторных прогонов подряд дают одинаковый результат. Результат не меняется, если системная дата сдвинута на любое время, в том числе позже 2030 года.
- **SC-004**: Полный прогон тестов доменного ядра занимает не более 5 секунд на обычной машине разработчика и не требует сети, базы данных или внешних сервисов.
- **SC-005**: По истории версий для каждого из двух методов ревьюер за 1 минуту находит пару фиксаций «падающие тесты → реализация» в правильном порядке.
- **SC-006**: Ревьюер сверяет сущности `DESIGN.md` §4 с ядром и не находит ни одного пропущенного поля или сущности.

## Assumptions

- Чтение относится только к текстовым изданиям (TextBook), у которых есть число страниц. Аудиокниги в эту фичу не входят.
- Число страниц издания у чтения всегда ≥ 1. Создание и валидация самого чтения (конструктор) в рамках фичи не требуются, если это не понадобится для тестов.
- Рассинхрон с `DESIGN.md` принят сознательно по приоритету указаний чата: в дизайн-документе статус хранится в ShelfItem, оценка — в Review, а процент считается по ReadingLog; здесь статус, прогресс и оценка принадлежат «Чтению». Как связать «Чтение» с ShelfItem, Review и ReadingLog, решаем вне этой фичи.
- Переходы в «брошено» и обратно, правка оценки после завершения и сохранение чтения в хранилище в эту фичу не входят.
- Технические рамки поставки задал пользователь. Они передаются в `/speckit-plan` и сознательно не раскрываются в требованиях: язык Go; сигнатуры `func (r *Reading) UpdateProgress(page int) error` и `func (r *Reading) Complete(rating int, finishDate time.Time) error`; табличные тесты через `t.Run` в файлах `*_test.go`; текущий момент по умолчанию — `time.Now()`.
