# ReadingTracker Constitution

## Core Principles

### I. Test-First Development (NON-NEGOTIABLE)
Разработка ведётся строго по TDD. Для каждого метода/поведения тесты пишутся ПЕРВЫМИ,
запускаются и ОБЯЗАНЫ упасть (фаза Red), и только после этого пишется реализация,
доводящая их до зелёного (фаза Green). Писать код реализации метода раньше, чем для него
существует падающий тест, ЗАПРЕЩЕНО. Падение теста до реализации обязательно: это защита
от ложноположительных тестов. Рефакторинг допускается только при зелёных тестах.
**Rationale:** учебная цель проекта — доказуемая дисциплина TDD; падающий тест до кода
гарантирует, что тест действительно проверяет поведение, а не проходит случайно.

### II. Traceable Red→Green Commits (NON-NEGOTIABLE)
История коммитов ОБЯЗАНА доказывать, что метод был покрыт тестами ДО его реализации.
На каждый метод создаётся МИНИМУМ два коммита в строгом порядке:
- `test: add failing tests for <Сущность>.<Метод>` — тесты существуют и падают;
- `feat: implement <Сущность>.<Метод> logic` — те же тесты становятся зелёными.

Коммит с падающими тестами ОБЯЗАН предшествовать коммиту реализации. ЗАПРЕЩЕНЫ
squash, amend или rebase, которые скрывают, схлопывают или переставляют «красный»
коммит и тем самым ломают прослеживаемость Red→Green.
**Rationale:** проверяющий должен по git-истории однозначно увидеть, что покрытие тестами
предшествовало реализации, без доверия на слово.

### III. Separation of Tests from Implementation
Тестовый код физически отделён от кода реализации: тесты располагаются в отдельных
файлах/каталогах/модулях согласно соглашениям соответствующего сервиса и НЕ смешиваются
с production-кодом в одних файлах. Тестовые зависимости и утилиты не попадают в
production-сборку сервиса.
**Rationale:** чистое разделение упрощает ревью Red→Green, предотвращает утечку тестовой
логики в продакшн и делает границу «тест vs реализация» однозначной.

### IV. Microservices Architecture
ReadingTracker — микросервисное приложение. Бэкенд состоит из независимо развёртываемых
сервисов; каждый сервис владеет своими данными, и прямой доступ к хранилищу чужого сервиса
ЗАПРЕЩЁН. Межсервисное взаимодействие идёт только через явные контракты (API/события),
а не через общую схему БД. Внешние зависимости (например, Google Books API) изолируются
за границей сервиса и подменяются в тестах.
**Rationale:** независимость сервисов и владение данными — базовое условие микросервисной
архитектуры; оно же делает каждый сервис независимо тестируемым по TDD.

### V. Contract-First HTTP API
Единственный клиентский интерфейс версии — HTTP API (web/mobile появятся позже). Поведение
сервиса определяется его контрактом; контракт описывается и покрывается тестами ДО
реализации (в соответствии с принципами I–II). Изменение контракта требует предварительных
контрактных тестов. Правила доступа и инварианты предметной области берутся из `DESIGN.md`
(с учётом раздела «Источник истины и приоритеты»).
**Rationale:** контракт — внешняя граница сервиса; фиксируя его тестами первым, мы защищаем
потребителей от незаявленных изменений и держим API предсказуемым.

## Источник истины и приоритеты (Source of Truth & Precedence)

- `DESIGN.md` — authoritative источник по предметной области и продуктовым границам
  ReadingTracker (сущности, сценарии, правила доступа, инварианты).
- При КОНФЛИКТЕ приоритет имеют промпты/явные указания пользователя в текущем чате,
  а не `DESIGN.md`. `DESIGN.md` применяется там, где чат ничего не уточняет.
- Инварианты предметной области из `DESIGN.md` (раздел 7) ОБЯЗАНЫ быть покрыты тестами
  и соблюдаться реализацией.
- Пункты из `DESIGN.md`, сознательно не зафиксированные (раздел 8: СУБД, формат URL,
  структура пакетов и т. п.), остаются свободой реализации и не являются нарушением,
  пока не противоречат этой конституции или указаниям чата.

## Рабочий процесс и контроль качества (Development Workflow & Quality Gates)

- **Цикл на метод:** Red (пишем и коммитим падающие тесты) → Green (реализуем, тесты
  зеленеют, коммитим) → при необходимости Refactor на зелёных тестах.
- **Минимум два коммита на метод** в порядке `test:` → `feat:` (Принцип II).
- **Ревью/приёмка** ОБЯЗАНЫ проверить по git-истории, что коммит с падающими тестами
  предшествует коммиту реализации; при отсутствии «красного» коммита изменение
  отклоняется.
- **Разделение тестов и кода** (Принцип III) проверяется при ревью.
- **CI/локальный прогон:** на коммите `test:` соответствующие тесты падают, на коммите
  `feat:` — проходят; обе фазы воспроизводимы.
- **Границы сервисов** не нарушаются: отсутствует прямой доступ к чужим данным, внешние
  API изолированы и мокируются в тестах.

## Governance

Эта конституция имеет приоритет над прочими практиками проекта. При конфликте с иными
договорённостями действует конституция (а продуктовые детали — согласно разделу «Источник
истины и приоритеты»).

- **Поправки** вносятся с письменным обоснованием, обновлением версии и прохождением
  ревью.
- **Версионирование (semantic versioning):**
  - MAJOR — несовместимое удаление/переопределение принципов или правил управления;
  - MINOR — добавление принципа/раздела или существенное расширение требований;
  - PATCH — уточнения формулировок, опечатки, несмысловые правки.
- **Проверка соответствия:** каждый PR/ревью обязан подтверждать соблюдение принципов,
  в особенности I и II (Test-First и прослеживаемость Red→Green).
- Для продуктовых и предметных деталей в ходе разработки используется `DESIGN.md`
  с учётом приоритета промптов текущего чата при конфликтах.
